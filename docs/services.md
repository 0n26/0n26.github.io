# Архитектура сайта и воркеров

| Где | За что отвечает |
| --- | --- |
| Корень (`0n26.github.io`) | React/Vite/PWA на GitHub Pages. `src/app/` — оболочка и проверка сессии перед открытием маршрутов; `src/pages/` — экраны и их состояние; `src/components/` — общие компоненты и плеер; `src/routes/` — URL; `src/catalog/` и `src/sources/` — каталог и адаптеры без React. [`AGENTS.md`](../AGENTS.md) задаёт границы слоёв, [README](../README.md) — контракт источников. |
| `services/gateway` ([0n26-gateway](https://github.com/0n26/0n26-gateway), приватный) | Единственный публичный Worker: HTTP API, CORS для origin Pages, проверка сессии и допуск к данным. Вызывает внутренние сервисы через Service Bindings. Читает индекс из закрытого Workers KV; сайт не отдаёт. |
| `services/identity` ([0n26-identity](https://github.com/0n26/0n26-identity), приватный) | Внутренний Worker без публичного URL: OAuth Shikimori, сессии, допуск и профили. Владеет собственной D1. |

Браузер обращается к Gateway по HTTPS; Identity недоступен напрямую. Shikimori возвращает браузер на `https://0n26.github.io/auth/callback`. Клиент передаёт код через Gateway, а Identity проверяет одноразовый `state` и привязку к вкладке. Код и токены Shikimori не хранятся на клиенте; токен сессии сайта остаётся в `sessionStorage`. Защищённые ответы не попадают в HTTP-кэш или PWA; список допуска, профили и индекс не публикуются с сайтом. Старый `0n26-backend` — справочник, не часть сборки.

## Получение исходников и локальные проверки

Обычный `git clone` и `npm ci` в корне достаточны для фронтенда. Для доступа к сервисам сначала войдите в GitHub под учётной записью с правом чтения нужного приватного репозитория. Затем из корня получите только нужные submodule:

```sh
git submodule update --init -- services/gateway services/identity
```

Не используйте `--recursive` и `--remote`: корень фиксирует точные коммиты, а у Gateway есть собственные закреплённые зависимости `frontend` (общие адаптеры и генератор индекса) и `identity` (локальная интеграция). Получайте их из checkout Gateway только по необходимости, тоже без рекурсии. `services/identity` и `services/gateway/identity` — разные рабочие копии одного сервиса: правьте одну, а интеграцию запускайте с зафиксированной или явно выбранной ревизией. При `404` или `Repository not found` проверьте права на приватный репозиторий, а не меняйте его видимость. Публичный CI и публикация Pages не скачивают сервисы; приватные токены им не нужны.

```sh
npm run check                         # из корня: типы, тесты и сборка сайта
(cd services/gateway && npm ci && npm run check)
(cd services/identity && npm ci && npm run check)
```

Перед изменением сервиса прочитайте `services/<имя>/AGENTS.md` и `README.md`. Они описывают его контракт, переменные и точные команды. Перед сборкой Gateway выполните `git -C services/gateway submodule update --init -- frontend`; для запуска интеграции подключите там и `identity` по README Gateway. Для локального окружения используйте тестовое приложение OAuth и локальные D1/KV. Production callback и origin нельзя считать рабочими с `localhost`. Не запускайте продакшен-миграции и деплой для обычной проверки.

## Изменение границ и версий

1. Правьте код в репозитории-владельце на ветке от его `main`. Submodule по умолчанию открывается на detached HEAD: создайте ветку в самом сервисе, а не коммитите его файлы в корень. Для каждого затронутого репозитория — свой PR, `verify` и правила [CONTRIBUTING](../CONTRIBUTING.md).
2. Если меняется контракт, перечислите поставщика и потребителей: `Identity RPC → Gateway HTTP → клиент`. Добавляйте совместимый контракт у поставщика, затем обновляйте потребителей. Проверяйте ошибки и отказы на каждой затронутой границе. Порядок деплоя и отсутствие несовместимого окна фиксируйте в описании PR. Сервисы выпускают версии независимо; обновление gitlink само ничего не деплоит.
3. После слияния PR сервиса обновите указатель на конкретный коммит его `main` или релизный тег в корневом PR. Укажите SHA и ссылку на PR сервиса. Не закрепляйте коммиты, существующие только локально или в ветке, которую удалят. Обновите также нужный указатель внутри Gateway, если менялась его зависимость: корневая ревизия его внутренний pin не заменяет.

## Как добавить сервис

1. Выделяйте Worker только если у области есть собственная ответственность, данные или причина для независимого деплоя. Новый источник аниме сам по себе не сервис: начните с `src/sources/` и [контракта адаптеров](../README.md#подключение-источника).
2. Создайте отдельный приватный репозиторий `0n26-<имя>` и подключите его как Git submodule `services/<имя>` после того, как в сервисе появится стабильный коммит. Имя описывает область, а не транспорт. Не объявляйте сервисы npm workspace корневого сайта.
3. Минимальная структура: `src/index.ts` — точка входа Worker и контракт RPC; доменная логика — в `src/`; `tests/` — проверяемые сценарии; `migrations/` — только если есть БД. В корне сервиса: `cloudflare.config.ts`, `package.json` и lockfile, `README.md`, `AGENTS.md`, workflow с `verify`. Для конфигурации текущего стека используйте `cf`. В README укажите владельца данных, API/RPC, bindings, имена секретов без значений и команды проверки. В `AGENTS.md` — границы и правила сервиса, не копию корневой инструкции.
4. По умолчанию новый Worker не имеет публичных роутов, `workers.dev` и preview URL. Gateway подключает его typed RPC через Service Binding. Сервис проверяет входные данные на своей границе и владеет записями в своём хранилище; не подключайте его таблицы к другим Worker. Миграции только добавлением. Секреты — в Cloudflare bindings или игнорируемом локальном `.dev.vars`; не логируйте их, `Authorization`, OAuth `code`/`state` или содержимое запросов входа.
5. Добавьте проверки контракта и отказов доступа в `verify` сервиса. Изолированный запуск не должен зависеть от продакшен-секретов и данных. Если меняете публичный сайт, корневой `npm run check` и проверка в браузере обязательны отдельно.
