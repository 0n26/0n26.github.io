# Участие в проекте

1. Создайте одну ветку и один PR на задачу. Не пушьте в `main` и не обходите защиту ветки.
2. Заголовок PR — [Conventional Commits](https://www.conventionalcommits.org/), например `fix(player): восстановить позицию при смене качества`. Это тема squash-коммита. Для несовместимых изменений используйте `!` после типа/области или футер `BREAKING CHANGE: ...` в описании PR.
3. Заполните шаблон, запустите `npm run check`. Для UI опишите проверку в браузере, включая ошибки и мобильную ширину там, где это применимо. Укажите участие ИИ, если он использовался.
4. Требуется зелёный `verify`, разрешённые замечания и squash merge сопровождающим. Отдельный обязательный ревьюер не нужен; агент не одобряет собственный PR и не сливает PR, даже если технически имеет доступ.

## Релизы

Для PR из любых репозиториев CI запускает один обязательный `verify`. Править версию и `changelog.md` в PR не нужно. После squash merge `fix`, `perf`, `revert` и `deps` повышают patch, `feat` — minor, несовместимое изменение — major. Остальные типы без признака несовместимости не выпускают релиз.

Под `## Изменения` в PR опишите, что изменилось для пользователя. GitHub переносит заголовок и описание PR в сообщение squash-коммита: не меняйте его и не удаляйте номер PR при слиянии. Заметки берутся из сообщения коммита без разделов «Проверка», «Риски» и служебных подписей.

Версия, lockfile и история изменений сохраняются в коммите релизного тега; `main` остаётся без бот-коммитов. GitHub Pages собирается из последнего коммита `main` с версией и changelog из последнего тега, в том числе после PR без повышения версии. Ручной запуск **Publish to GitHub Pages** из `main` завершает ожидающие релизы и публикует сайт повторно.

Для первого PR из форка GitHub может требовать **Approve workflows to run**. Сопровождающий запускает CI после проверки изменений; право на запись в форк и секреты для его CI не нужны.
