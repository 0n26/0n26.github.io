# Участие в проекте

1. Создайте одну ветку и один PR на задачу. Не пушьте в `main` и не обходите защиту ветки.
2. Заголовок PR — [Conventional Commits](https://www.conventionalcommits.org/), например `fix(player): восстановить позицию при смене качества`. Это тема squash-коммита. Для несовместимых изменений используйте `!` после типа/области или футер `BREAKING CHANGE: ...` в описании PR.
3. Заполните шаблон, запустите `npm run check`. Для UI опишите проверку в браузере, включая ошибки и мобильную ширину там, где это применимо. Укажите участие ИИ, если он использовался.
4. Требуется зелёный `verify`, разрешённые замечания и squash merge сопровождающим. Отдельный обязательный ревьюер не нужен; агент не одобряет собственный PR и не сливает PR, даже если технически имеет доступ.

## Релизы

CI проверяет релизные файлы до установки зависимостей и запуска `npm run check`. Если нужна новая версия, GitHub App обновляет `package.json`, `package-lock.json` и `changelog.md` в исходном PR из ветки этого репозитория. Полный `verify` проходит только на коммите с актуальными файлами; до его успеха слияние заблокировано. `fix`, `perf`, `revert` и `deps` повышают patch, `feat` — minor, несовместимое изменение — major. Остальные типы без признака несовместимости не выпускают релиз. Отдельный release PR не создаётся.

В описании PR под `## Изменения` укажите, что изменилось для пользователя, где это видно и какие есть ограничения. Заголовок и описание PR становятся сообщением squash-коммита, из которого заранее составляются заметки. Не редактируйте сообщение в диалоге squash merge. «Проверка», «Риски» и служебные подписи в заметки не попадают. После изменения заголовка или описания релизные файлы нужно обновить. Если `main` продвинулась, сначала обновите ветку PR; при конфликте в журнале сохраните историю `main` и подготовьте запись заново.

После каждого слияния в `main` GitHub Actions собирает и публикует актуальный коммит `main` на GitHub Pages, даже если версия не изменилась. При повышении версии workflow также создаёт тег и GitHub Release. Ручной запуск **Publish to GitHub Pages** из `main` повторно публикует сайт из `main` без создания релиза.

### PR из форка

GitHub App не имеет доступа на запись в чужие форки. Для релизного PR обновите и отправьте свою ветку из `main` основного репозитория, затем запустите с Node.js 24 и авторизованным `gh` из корня проекта:

```sh
node scripts/release.mjs sync https://github.com/0n26/0n26.github.io/pull/123
```

Замените `123` на номер своего PR. Проверьте и закоммитьте изменённые `package.json`, `package-lock.json` и `changelog.md`, затем отправьте их в ту же ветку. Если GitHub ожидает **Approve workflows to run**, сопровождающий запускает CI после проверки изменений. Обязательный `verify` должен пройти на последнем коммите PR.

### Настройка GitHub App

1. Создайте приватный [GitHub App](https://github.com/settings/apps/new), отключите webhook и выдайте только **Repository permissions → Contents: Read and write**. Установите App только в этот репозиторий. Не добавляйте его в исключения правил `main`.
2. В **Settings → Environments** создайте `release-bump`. В **Deployment branches and tags** разрешите только ветку `main`.
3. В окружении `release-bump` задайте переменную `RELEASE_APP_CLIENT_ID` и секрет `RELEASE_APP_PRIVATE_KEY`. Не храните ключ в репозитории. Workflow **Bump version in pull request** использует ключ только для записи трёх релизных файлов поверх актуального SHA ветки PR.
