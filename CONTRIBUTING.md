# Участие в проекте

1. Создайте одну ветку и один PR на задачу. Не пушьте в `main` и не обходите защиту ветки.
2. Заголовок PR — [Conventional Commits](https://www.conventionalcommits.org/), например `fix(player): восстановить позицию при смене качества`. Это тема squash-коммита. Для несовместимых изменений используйте `!` после типа/области или футер `BREAKING CHANGE: ...` в описании PR.
3. Заполните шаблон, запустите `npm run check`. Для UI опишите проверку в браузере, включая ошибки и мобильную ширину там, где это применимо. Укажите участие ИИ, если он использовался.
4. Требуется зелёный `verify`, разрешённые замечания и squash merge сопровождающим. Отдельный обязательный ревьюер не нужен; агент не одобряет собственный PR и не сливает PR, даже если технически имеет доступ.

Для работы с приватными Git submodule следуйте [руководству по сервисам](docs/services.md#изменение-границ-и-версий). Корневой CI проверяет сайт без их checkout; проверка Worker выполняется в репозитории сервиса.

## Релизы

Для PR из любых репозиториев CI запускает один обязательный `verify`. Править версию и `changelog.md` в PR не нужно. После squash merge `fix`, `perf`, `revert` и `deps` повышают patch, `feat` — minor, несовместимое изменение — major. Остальные типы без признака несовместимости не выпускают релиз.

Под `## Изменения` в PR опишите, что изменилось для пользователя. GitHub переносит заголовок и описание PR в сообщение squash-коммита: не меняйте его и не удаляйте номер PR при слиянии. В следующий релиз входят все изменения в `main` после предыдущего тега, включая не повышающие версию, но без служебных PR синхронизации changelog. Заметки берутся из сообщений коммитов без разделов «Проверка», «Риски» и служебных подписей. Исправления истории из `main` попадут в следующий тег, если файл в `main` уже содержит последнюю опубликованную версию.

Версия и lockfile сохраняются в коммите релизного тега. Для GitHub Pages CI подставляет версию и changelog из тега в выбранный коммит `main` и публикует сборку без индекса каталога. Gateway развёртывается отдельно и обслуживает только вход и API.

Перед публикацией клиента с прямым возвратом из Shikimori разверните поддержку `POST /auth/start` и `POST /auth/complete` в Gateway и Identity и проверьте, что Shikimori разрешает точный URI `https://0n26.github.io/auth/callback`. Сборка содержит `auth/callback.html` для этого адреса без перенаправления и `auth/callback/index.html` для варианта со слешем. Не удаляйте старые маршруты входа до завершения перехода.

## Обновление каталога

Приватный CI `0n26-catalog` собирает снимок закреплённой версией `frontend/scripts/catalog-index.mjs` и обновляет закрытый Workers KV. Настройка и запуск описаны в `services/catalog/README.md`. Gateway не пишет снимок; Pages и публичный репозиторий его не публикуют.

Неудачное обновление не перезаписывает последний полный индекс. До первого успешного сбора и после истечения срока годности индекса (семь суток) Gateway запрашивает каталог у источников.

## Синхронизация changelog

После релиза workflow копирует `changelog.md` из тега в служебную ветку `automation/sync-changelog` и открывает `docs` PR. GitHub Auto-merge сливает его только после обязательных проверок; новый релиз не создаётся. Служебную ветку обновляет только бот.

Для синхронизации включите **Settings → General → Allow auto-merge** и выдайте установленному `0n26-release-bump` права **Contents: Read and write** и **Pull requests: Read and write**. Используются `RELEASE_APP_CLIENT_ID` и `RELEASE_APP_PRIVATE_KEY` из окружения `release-bump`, ограниченного `main`. Исключения из правил защиты `main` не нужны.

Для первого PR из форка GitHub может требовать **Approve workflows to run**. Сопровождающий запускает CI после проверки изменений; право на запись в форк и секреты для его CI не нужны.
