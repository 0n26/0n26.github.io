# Участие в проекте

1. Создайте одну ветку и один PR на задачу. Не пушьте в `main` и не обходите защиту ветки.
2. Заголовок PR — [Conventional Commits](https://www.conventionalcommits.org/), например `fix(player): восстановить позицию при смене качества`. Это тема squash-коммита. Для несовместимых изменений используйте `!` после типа/области или футер `BREAKING CHANGE: ...` в описании PR.
3. Заполните шаблон, запустите `npm run check`. Для UI опишите проверку в браузере, включая ошибки и мобильную ширину там, где это применимо. Укажите участие ИИ, если он использовался.
4. Требуется зелёный `verify`, разрешённые замечания и squash merge сопровождающим. Отдельный обязательный ревьюер не нужен; агент не одобряет собственный PR и не сливает PR, даже если технически имеет доступ.

## Релизы

После успешных проверок GitHub App обновляет `package.json`, `package-lock.json` и `changelog.md` в исходном PR. `fix`, `perf`, `revert` и `deps` повышают patch, `feat` — minor, несовместимое изменение — major. Остальные типы без признака несовместимости не выпускают релиз. Первый `verify` блокирует слияние, пока файлы не обновлены; после бот-коммита все проверки запускаются снова. Отдельный release PR не создаётся.

В описании PR под `## Изменения` укажите, что изменилось для пользователя, где это видно и какие есть ограничения. Заголовок и описание PR становятся сообщением squash-коммита, из которого заранее составляются заметки. Не редактируйте сообщение в диалоге squash merge. «Проверка», «Риски» и служебные подписи в заметки не попадают. После изменения заголовка или описания бот обновляет ту же запись. Если `main` продвинулась, сначала обновите ветку PR; при конфликте в журнале сохраните историю `main`, бот добавит запись заново. Бот работает только для веток этого репозитория; для PR из форка сопровождающий переносит изменение во внутреннюю ветку.

После слияния GitHub Actions создаёт тег и GitHub Release из записанной версии и публикует сайт из тега. Ручной запуск **Publish releases to GitHub Pages** из `main` повторно публикует последний GitHub Release.

### Настройка GitHub App

1. Создайте приватный [GitHub App](https://github.com/settings/apps/new), отключите webhook и выдайте только **Repository permissions → Contents: Read and write**. Установите App только в этот репозиторий. Не добавляйте его в исключения правил `main`.
2. В **Settings → Environments** создайте `release-bump`. В **Deployment branches and tags** разрешите только ветку `main`.
3. В окружении `release-bump` задайте переменную `RELEASE_APP_CLIENT_ID` и секрет `RELEASE_APP_PRIVATE_KEY`. Не храните ключ в репозитории. Workflow **Bump version in pull request** использует ключ только для безопасной записи трёх релизных файлов поверх проверенного SHA.
